Prefect 3.8.6 OSS server (docker compose: prefecthq/prefect:3.8.6-python3.12 running `prefect server start`, backed by postgres:16), everything on one m7i.xlarge (4 vCPU). The flow runs as a plain Python process (the flow function is called directly, no deployment and no work pool); each of the N tasks is a real Prefect task invoked synchronously (no .submit()), so each is its own server-tracked task run and they execute strictly in order. One warmup flow run, then 5 measured reps, all inside one client process so lazy imports are already warm; 3s settle between runs to let Prefect drain its background state/log writers. Timings come from the Prefect server's Postgres database, table task_run_state: created_at = PENDING state timestamp, started_at = RUNNING, completed_at = terminal (COMPLETED). Prefect 3 orchestrates task runs client-side and flushes state changes to the server in batches, so task_run.created (the server row-insert time) lags the real orchestration by roughly 40-130 ms and was deliberately not used; task_run_state.timestamp is the moment the engine created the state. Before reading, each flow run was polled until the flow run and all N task runs were terminal, end_time was set on every task run, at least 3 states per task run were persisted, and the counts were stable across two consecutive 1s polls. Cross-check: the PENDING/RUNNING/terminal state timestamps match the denormalised task_run.start_time / end_time columns exactly (0 ms drift). Verified that every task run had a NULL cache_key and run_count = 1, so there were no cache hits and no retries. Caveat: the Prefect image ships CPython 3.12, where the naive fibo(33) costs about 0.287s, versus about 0.52s for CPython 3.9 on the same box, so the fibonacci_10_33 total is dominated by an interpreter-dependent compute floor of roughly 2.87s; compare orchestration overhead (total minus summed task durations) rather than raw totals against an engine running a different CPython. Caveat: Prefect 3 executes tasks in the same process as the flow, so these numbers measure in-process task-engine overhead plus asynchronous state writes to the server, not per-task process or container scheduling; there is no worker pool, and "workers" is recorded as 1 meaning one flow-run process.
